# MiMo three-token drafting

Historical recursive-block baseline. See [native blocks 0/1/2](2026-09-22-mimo-native-mtp3.md) for its successor.

Extends the one-token native MTP implementation to `engine.mtp_depth=3`.
A verification pass covers the pending token plus three draft tokens. Both
single-request and two-request CUDA graphs support the chain; the latter
uses eight verification rows.

This uses **recursive block-zero drafting**, following the currently published
[vLLM MiMoV2MultiTokenPredictor](https://github.com/vllm-project/vllm/blob/main/vllm/model_executor/models/mimo_v2_mtp.py),
which sets `num_mtp_layers = 1` and feeds normalized draft outputs into the
next invocation. It does not execute checkpoint blocks one and two. Native
multi-block training and cache alignment would need separate implementation
and validation; three draft tokens does not imply three distinct blocks.

The normalized output for every draft row is retained so the verifier can
select the last accepted row. Chain K/V has a separate rollback copy from
the pre-draft snapshot. After producing the proposals, chain K/V is restored;
only verified-token catch-up advances draft history. Prefix snapshot size
and count are unchanged. Added per-rank allocation is 36 MiB: one hidden-row
buffer and a separate two-request chain cache backup at the 2048-row chunk size.

Capacity remains 262144 tokens/request, concurrency two, four snapshots,
11.336700439453125 GiB prefix allocation, HTTP port 30001.

## Matched short generation probes

Same two prompts and 256-token greedy settings as the depth-one report,
run separately and then concurrently. A fresh depth-one baseline was taken
before changing the service; no GPU tests overlapped it. All four depth-three
texts match the corresponding depth-one texts exactly, including cache reuse.
Rates below estimate 255 divided by first-nonempty-delta-to-completion seconds;
hidden special tokens can slightly affect absolute rates, not timing ratios.

| Probe | Depth one tok/s | Depth three tok/s | Ratio |
|---|---:|---:|---:|
| Interval merging, alone | 35.53 | 33.80 | 0.95x |
| Hash tables, alone | 33.27 | 31.58 | 0.95x |
| Interval merging, concurrent | 25.41 | 19.34 | 0.76x |
| Hash tables, concurrent | 24.54 | 18.83 | 0.77x |

Concurrent rates are per request. Across these probes, accepted proposals by
position were 336/380, 206/380 and 104/380 (88.4%, 54.2%, 27.4%). Server timings
show concurrent passes rising from 74–76 ms to 139–143 ms, while generated
tokens/pass/request rise from 1.82–1.93 to 2.60–2.77. Thus deeper drafting is
implemented but does **not** provide a speedup for this short-prompt sample.
This does not establish performance at a full 256K context.

The exact `ChatCompletionsClient -> RecordingTransport -> UrllibModelTransport`
harness completed six turns: **11/11 emitted tool calls had their required
arguments and executed successfully** against the read-only Astroid checkout.
The first request was asserted equal to the user's original recorded payload.
Three additional streamed argument checks passed for shell, integer offset/
limit file reading, and a two-required-field write call; generated shell/write
operations were not executed. These checks overlapped harness turns, exercising
two constrained requests. This is tool transport/argument validation, not a
full repair-quality evaluation. No server requests failed.

The depth-three configuration remains selected at the user's request; depth
one is faster in these measurements. Warmed-repeat results follow below.



## Final verification

The warmed repeat again matched all four depth-one texts. Rates were
33.56/31.56 tok/s alone and 19.26/18.75 tok/s per concurrent request:
0.944x/0.948x and 0.758x/0.764x the fresh depth-one baseline. This confirms
roughly 5–6% lower single-request throughput and 24% lower concurrent
throughput in this sample; no speed improvement is claimed.

Final health is OK and the scheduler is idle. All 17 requests completed with
zero failures/cancellations, 14 structured tool calls and nine prefix hits.
Both ranks have identical binary hashes and effective configuration digests,
with no error lines in either log. Available node memory is 7.3/7.6 GiB.
The maintenance lock was released. Depth three remains live and selected by
the deployment example; the preserved depth-one configuration is the faster
option for the measured workloads.
